### How kubelet auths as server to its clients

Kubelet as server provides certificate to its client, for ex., API server.
There are different ways these certificates can be generated

<details>
<summary>Answer</summary>
1. We can generate certificates, sign them by cluster CA and specify locations in <code>/var/lib/kubelet/config.yaml</code> with these parameters:
   
   - <code>tlsCertFile</code>
   - <code>tlsPrivateKeyFile</code>
  
2. If we do not specify these and the parameter <code>serverTLSBootstrap</code> is **false** - kubelet will generate default self-signed certificate

3. If <code>serverTLSBootstrap</code> is **true** - kubelet will request certificates via CSR from API server. They will be signed by kube-controller-manager

    - Kubelet submits CSR
    - API server stores CSR object
    - Approver (manual or automatic) approves the CSR
    - kube-controller-manager signs using cluster-signing-key-file
    - Signed certificate is written back into the CSR and kubelet downloads it

To see where the certificate that kube-controller-manager used to sign the CSR is stored, inspect kube-controller-manager runtime flags
```
ps -ef | grep '[k]ube-controller-manager' | grep cluster-signing
--cluster-signing-key-file
--cluster-signing-cert-file

```
#### how to check if the certificate is signed by custom signer
not kube-controller-manager

We can inspect the certificate to find the signer. The path to the certificate should be in Kubelet configuration <code>/var/lib/kubelet/config.yaml</code>

```
openssl x509 -in kubelet.crt -text -noout
```

Check **Issuer** and Authority Key Identifier (**AKI**). For example,

```
Issuer: CN=Corp Kubernetes Intermediate CA
```
This is not the default kubeadm CA. We can also check **signerName** in CSR.

To find the signing chain, try verifying certificate against known CAs
<code>openssl verify -CAfile ca.crt kubelet.crt</code>

If we can confirm that the signer is custom, there must be a controller deployed on the cluster that watches CSRs with a particular signerName

##### Find external signer
If signerName is <code>company.example.com/kubelet-serving</code>, we can look for deployments or pods with the name containing company

<code>kubectl get deployment -A | grep company</code>

### Find out how the certificate is generated on default kubeadm cluster

<details>
<summary>Answer</summary>

To find the certificate, we can first check if  **tlsCertFile** is specified in kubelet configuration <code>/var/lib/kubelet/config.yaml</code>. It is not specified, so we check **serverTLSBootstrap**. If it is true, the certificate is procured via certificates API. It is not specified either, so we assume that kubelet generates the certificate by itself. In order to find its location, we can search through K8s source code.

```
openssl s_client -connect localhost:10250 -showcerts
```

#### How does API server validate kubelet server certificate
Whenever API server acts as client to kubelet, it presents its client certificates, but it is also supposed to validate kubelet server certificate. If kubelet presents a self-signed certificate, how can API server trust it?
If we run for ex. <code>kubectl logs</code> - it works, so API server clearly trusts kubelet server. So we can assume that API server skips certificate verification.

We can use API server client certificates to query kubelet API with curl and see more output

```
curl \
  --cert /etc/kubernetes/pki/apiserver-kubelet-client.crt \
  --key /etc/kubernetes/pki/apiserver-kubelet-client.key \
  https://localhost:10250/healthz

```

This command fails, unless we run it with **-k**. The error confirms that the certificate is not signed by CA that API server trusts

```
(60) SSL certificate problem: self-signed certificate in certificate chain
```

Now the question is - how is API server configured to accept the certificate it doesn't trust?
The documentation https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/?utm_source=chatgpt.com shows that the authority could be specified by this option <code>--kubelet-certificate-authority</code>. This is the CA certificate that should validate the certificate presented by kubelet when it acts as server.


We can inspect API server flags in case it specifies kubelet CA in <code>--kubelet-certificate-authority</code>

```
ps -ef | grep '[k]ube-apiserver'
```

The option is not used. The docs do not mention **--kubelet-insecure-tls** either, so the communication must be secure.

### Configure kubelet to procure server certificate via Certificate API

<details>
<summary>Answer</summary>

1. in <code>/var/lib/kubelet/config.yaml</code> add 

```
serverTLSBootstrap: true
```

2. restart kubelet service
3. Kubernetes does not automatically approve kubernetes.io/kubelet-serving CSRs. Anyone who obtains a valid serving certificate could impersonate a kubelet to clients that trust your cluster CA. For that reason, Kubernetes requires a human or an external controller to verify that the CSR is legitimate before approving it. 

```
kubectl get csr -A
kubectl certificate approve <csr>

```
4. Now we can inspect the generated certificate in .spec.status of the approved CSR object

```
kubectl get csr mycsr -o jsonpath='{.status.certificate}' | base64 -d | openssl x509 -text -noout
```
Unlike previous self-signed certificate, we can see here 

```
    Issuer: CN = kubernetes
        Subject: O = system:nodes, CN = system:node:k8s-playground
```


5. In <code>/var/lib/kubelet/pki</code> we can find the new **kubelet-server-current.pem**

### Why is kubelet serving CSR not approved automatically while kubelet refreshes its client cert, the CSR is approved by built-in approver?

##### kubelet as client
If an attacker submits CSR for kubelet as client to API server, it does not mean it will automatically approved.
The approver verifies things such as:

- the requester is already an authenticated kubelet,
- the requested subject matches that kubelet,
- it's a renewal rather than an attempt to become a different node.

When kubelet submits CSR for renewal, it already has a valid client certificate:

CN = system:node:worker-1

It authenticates to the API server using that certificate. Now it says: "I'd like another certificate with exactly the same identity." That's much easier to validate automatically.

And when kubelet submits first certificate request, it uses bootstrap token


##### kubelet serving
Kubelet serving certificate lets other components trust it. The risk here is different. Suppose a node requests a certificate with SANs:

```
DNS: api.internal.company.com
IP: 10.0.0.1
```

If that certificate were automatically approved, and clients trust the cluster CA, that node could impersonate another service. Approving serving certificates safely requires checking things like:

- Do the SANs correspond to this node?
- Is the node allowed to use those IPs?
- Is the hostname legitimate?

Those checks are environment-specific, which is why Kubernetes leaves approval to an administrator or an external approver.


A client certificate says: "I am node X."

A serving certificate says: "Anyone connecting to this hostname/IP is really talking to node X."
